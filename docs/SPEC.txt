#1 Open Public Data Platform — Spec
 · 
#2 Problem and goal
Public data is free but scattered. Every source has its own API, codes, file formats and update schedule. A simple question like "how did India's unemployment move against its exports over 5 years" means hitting 3 portals, cleaning 3 formats and matching country codes by hand. LLMs make it worse: they answer from memory with stale or made-up numbers.
We build an open-source, self-hostable platform that pulls public data from many sources into one catalog and one query layer. A person, a script or an AI agent can find a dataset, query it the same way whatever the source, and get every number back with its source cited.
v1 must do five things:
Find: search all sources in plain words ("unemployment rate India") and get matching series.
Query: one SQL / REST shape for every source.
Combine: join across sources on shared keys (country, year, product code, company id).
Cite: every value traces back to source, dataset, retrieval time and licence.
Extend: a new source is a new folder (often just a config file), not a change to the core.
Questions v1 should answer end to end, used as acceptance tests:
Unemployment rate for India, Bangladesh and Vietnam, 2015 to latest year.
What India exported to the US by HS chapter in the latest year, and the change from 5 years earlier.
Which US-listed companies in one industry grew revenue fastest in their last fiscal year.
CPI inflation vs policy rate across G20 countries over the last 10 years.

Known gaps (no open source, or out of scope)

Survey microdata (e.g. PLFS unit-level records). Non-goal: privacy and size.
Real-time data. Most official stats are monthly, quarterly or annual. We show the latest release date on every series instead of pretending it is live.
#2 Architecture
Six layers, top to bottom. The connector contract is the only place a new source touches; everything below it is shared.
Data flows down. The dashed line is the on-demand path: a query for a series we haven't ingested goes back through the same connector, under the same rate limits.
Main flows
Scheduled ingest. The scheduler picks a due dataset, the connector fetches it through the shared HTTP client, the raw response is saved, normalize maps it to the schema, the harmoniser maps codes, and new Parquet parts plus catalog rows go live with one manifest swap.
Query, ingested series. Client calls REST or MCP, the query service resolves series in the catalog, DuckDB reads Parquet, rows come back with citations.
Query, remote series. The catalog marks it remote, so the connector fetches it under a budget, the result is cached, and rows come back with citations. Popular remote series can be promoted to the scheduled core.
New source. Add a folder in connectors/, pass the contract tests, discover fills the catalog, data arrives on schedule or on demand. No change to the core.
Deployment (v1): docker compose with three services sharing one data/ volume: api (FastAPI + MCP over HTTP), worker (scheduler + ingestion), web (Next.js). The web service is optional in v1.
#2 Connector SDK: adding a source
A new source is one folder under connectors/. Most sources need only a manifest; code is the last resort.
Config only. The source speaks a protocol we already support (SDMX, CKAN, a plain CSV / XLSX / ZIP URL). Write manifest.yaml, done.
Config + mapping. Files or REST with their own column names. Add mapping.yaml that maps columns to the observation schema.
Custom code. Anything else. Write a Python class that implements the contract below.<![CDATA[connectors/

The contract every connector implements:<![CDATA[class Connector(Protocol):
    manifest: Manifest
    def discover(self) -> Iterable[DatasetMeta]:
        """List datasets and series: title, dimensions, unit, frequency, coverage.
        Feeds the catalog. No observations here."""
    def fetch(self, req: FetchRequest, http: HttpClient) -> Iterable[RawChunk]:
        """Pull raw data for one dataset + filter. Uses the runner's HttpClient,
        which already does rate limiting, caching, retries and User-Agent."""
    def normalize(self, chunk: RawChunk) -> pa.Table:
        """Map raw rows to the observation schema. Pure function, no I/O."""]]>
Rules that keep connectors small and safe:
Connectors never write their own retry, cache or rate-limit logic. The runner hands them one shared HttpClient per source, so scheduled and on-demand fetches share the same budget.
normalize is pure, so CI tests it against recorded fixtures with no network.
Every connector must pass the contract test suite: manifest validates, discover returns at least one dataset with a licence, normalize output matches the schema, every geo / product code maps to a standard list or is flagged as unmapped.
A separate nightly job runs live smoke tests to catch upstream API changes. Failures open an issue; they don't block PRs.
Raw responses are kept, so a change to normalize bumps version and re-processes old raw snapshots without hitting the source again.
Scaffold: &lt;cli&gt; connector new &lt;id&gt; --kind sdmx|file|rest|custom generates the folder, manifest, fixture recorder and test file.
#2 Data model and harmonisation
All numeric data lands in one long-format observations table, so a cross-source join is a plain SQL join. Things that aren't time series (company records, filing lists) get their own typed tables. Harmonising keys is the real value-add, not storage.

The catalog holds sources, datasets, series (title, description, unit, frequency, geo and time coverage, licence, last update, status ingested or remote), codelists, and lineage (raw snapshot, connector version, request params).
Harmonisation rules
Countries. ISO 3166-1 alpha-3 is canonical. Each connector maps its own codes (UN M49 numerics, World Bank aggregates, IMF codes). Aggregates like EU27, World or income groups get region: codes and never mix with countries.
India specifics. India's fiscal year runs April to March, and PLFS publishes quarterly and annual rounds. Explicit period_start / period_end handles both. State-level codes (LGD) come in v1.1.
Products and industries. HS for trade, ISIC (and India's NIC) for industry. Store the source code plus the mapped code; concordance tables are data in the repo, not code.
Companies. LEI is the canonical ID when one exists. An entity_xref table links LEI, SEC CIK, ticker and ISIN, with the source and a match confidence. GLEIF maps ISIN and BIC; CIK to LEI needs name + address matching, so those links are flagged as inferred.
Units and currency. Keep units as published. Currency conversion happens only at query time on request, using an explicit exchange-rate series and date.
Revisions. Core datasets keep every vintage, so "what was known on date X" works. The long tail keeps the latest only.
#2 Storage, refresh and query
Ingestion writes immutable Parquet files; the API reads them through in-memory DuckDB views. That sidesteps DuckDB's single-writer lock and keeps the whole thing to one container plus a data folder.
Layout on disk<![CDATA[data/
  raw/]]>&lt;/]]>&lt;/]]>&lt;/...       # responses as fetched, gzipped
  obs/]]>&lt;/]]>&lt;/part-*.parquet           # tidy observations
  cache/]]>&lt;/...                              # on-demand results, with TTL
  catalog.sqlite                                  # WAL mode: one writer, many readers]]>
A refresh writes new Parquet parts, then swaps a small manifest file in one atomic rename. Readers never see half-written data.
The catalog is SQLite with FTS5 for keyword search. Embeddings for semantic search are optional and stored alongside.
Raw data, observations and cache can sit on local disk or S3-compatible storage. The hosted phase can move the catalog to Postgres without touching connectors.
Refresh
A built-in scheduler reads refresh from each manifest. No Airflow.
Incremental where the source allows it (OECD's UpdatedAfter, DBnomics' last-updates feed); full pull otherwise.
Jobs are idempotent and their state lives in the catalog. A failed job retries with backoff, then marks the dataset stale with the error.
On-demand fetch
When a query hits a series with status remote, the service asks its connector to fetch it under a budget (timeout, max rows), writes the result to cache/, and answers. If the source is rate-limited, it returns the series metadata plus a "retry after" hint instead of hanging.

#2 AI layer
The AI never answers numbers from memory: it finds a series, queries it, and the UI shows the citation from the tool result, not from the model's text. The MCP server is the one AI interface; the built-in chat is just another MCP client.

Built-in chat (web UI)
Bring your own key. One adapter layer covers OpenAI-compatible APIs, Anthropic and local models through Ollama.
The chat calls the same MCP tools. No private shortcut, so anything the chat can do, an external agent can too.
Guardrails
Every number shown has its unit, period and source next to it, rendered from the tool's citations[].
The answer shows the series ids and SQL used, so a person can re-run it.
No matching data means the answer says so. The system prompt forbids filling gaps from memory, and the UI flags any number in the reply that didn't come from a tool result.
Sandboxed Python (v1.1): off by default, a container with no network, CPU / memory / time limits, and a read-only mount of the Parquet files. Used for charts and stats SQL can't do.
Search quality is the hard part. An agent can only query what it can find. Each catalog entry gets a plain-text description and synonyms ("jobless rate" maps to unemployment); keyword search is the baseline and embeddings are optional. We keep an eval set of ~50 natural-language questions with the expected series ids, and track top-5 recall in CI.
#2 Licensing, provenance and source etiquette
Every dataset carries its licence in the catalog, and the platform enforces it: a self-hoster uses data under their own keys and terms, while a hosted instance serves only what may be redistributed.
Licence metadata is mandatory. Name, URL, attribution string and redistribute: yes | no | review. A connector without it fails the contract tests.
Hosted instance rules. Serve yes datasets from the shared store. no and review datasets are fetched only with the user's own key and are never cached for other users. Examples: FRED series with a third-party copyright notice, and UN Comtrade.
Attribution travels with the data. Every API response and MCP result has citations[]. CSV / Parquet exports ship with a SOURCES.md.
Provenance. Each observation file links to a lineage record: source URL, request params, retrieved_at, connector version, hash of the raw snapshot.
Rate limits. One limiter per source per process, shared by scheduled and on-demand fetches. Honour Retry-After. The SEC User-Agent with a contact email comes from config and is required to start. Never rotate keys or IPs to dodge limits.
No scraping where terms forbid it. File downloads respect robots.txt.
Code licence. Apache-2.0. Contributed connectors must be Apache-compatible, so no AGPL code (e.g. DBnomics fetchers) gets copied in.
Get the hosted-instance policy reviewed by someone who knows data licensing before any public launch.
#2 Roadmap
Four phases, each with an exit gate. Phase 3 only happens if Vikash decides to run a hosted instance.
